# RFC-002: Дисковый стриминг сэмплов и PCM-кэш банков

Статус: черновик · Владелец: saytomorrow-st · База: `main` (v0.1.61) · Только дизайн, кода нет.
Связано: `docs/rfc/001-sampler-sfz.md` (§3.3, §4, §7), `specs/068-sampler-streaming.md` (Шаг B), `docs/REALTIME.md`.
Реализация требует новой спеки `specs/069-sample-cache-streaming.md` (AGENTS.md: код только по спеке).

## 0. Проблема

`load_bank` декодирует весь банк из FLAC в `Arc<[i16]>` и держит его в `LoadedBank` до закрытия приложения.

| Банк | Файлов | FLAC | PCM i16 в RAM |
|---|---|---|---|
| Osiris Piano | 1242 | 460 MiB | ~2622 MiB |
| Salamander | — | — | ~1146 MiB |

На машине с 8 GiB процесс получает OOM-kill (`DEFAULT_RAM_BUDGET_MIB = 3072` слишком велик; пик при параллельном `decode_all` ещё выше). Требование владельца: любой ноутбук должен загрузить хотя бы один инструмент; установка должна «сразу распаковывать» банк; целостность файлов проверяется при каждой загрузке инструмента.

`specs/068` отложил стриминг (Шаг B) с допущением «оба банка влезают в 512 МиБ». Допущение устарело: условие запуска Шага B наступило. Данный RFC расширяет 068 и уточняет его (см. §3.5 про `mmap`).

## 1. Цели и не-цели

Цели:
- Osiris ≤ 512 MiB RSS (целевой коридор 300–400 MiB), загрузка инструмента за секунды при тёплом кэше.
- В аудиопотоке: ноль аллокаций, блокировок и I/O (контракт `docs/REALTIME.md`).
- PCM-кэш создаётся при `download_bank`; при отсутствии кэша строится в фоне с прогрессом в UI.
- Проверка целостности кэша при каждой загрузке инструмента, автоперестроение повреждённого.
- Офлайн-экспорт и golden-тесты не меняются.

Не-цели: новые DSP-функции; изменение `crates/audio-core/tests/golden/*.wav`; сжатие кэша; сетевой стриминг.

## 2. Варианты и выбор

| Вариант | RSS Osiris | Realtime-риск | Загрузка | Вердикт |
|---|---|---|---|---|
| A. Текущий: full decode в RAM | ~2.6 GiB | нет | десятки секунд | OOM, отклонён |
| B. PCM-кэш + mmap целиком + LRU страниц ОС | не ограничен (resident-страницы растут до 2.6 GiB), на 8 GiB зависит от ядра | page fault в аудиопотоке = скрытый I/O (запрет 068) | быстрая | не гарантирует ≤512 MiB, отклонён |
| C. FLAC по блокам + seek-таблица | мало | декодирование в disk-thread, CPU-нагрузка при 64+ голосах | быстрая без кэша | запасной путь (fallback), не основной |
| D (выбран). PCM-кэш + preload голов + disk-thread + SPSC-кольца | ~250–400 MiB | нет: аудиопоток читает только RAM | быстрая | выбран |

Обоснование: только D даёт жёсткую верхнюю границу RSS, не зависящую от политики страниц ОС. Для достаточно больших машин сохраняется режим `Preload` (все головы = весь сэмпл, если кэш умещается в бюджет): гибрид выбирается по бюджету, а не по флагу (§8).

Вариант B допустим только внутри loader-потока (там page fault безвреден), но `pread` проще и переносим на Windows, поэтому loader использует `pread`/`seek+read`, а `mmap` не используется (запрет 068 сохраняется).

## 3. Архитектура и структуры данных

```
download_bank ─► FLAC ─► cache builder ─► cache/*.pcm + manifest.json
                                              │
 load instrument ─► integrity check (bg) ─────┤
                                              ▼
 audio thread ◄── head (RAM, Arc<[i16]>)   SampleSource
      ▲  rtrb SPSC (ring на голос)             │
      └────────── loader thread ◄─ LoadRequest ┘  (pread из *.pcm)
```

### 3.1 Источник сэмпла

```rust
enum SampleSource {
    Resident(Arc<[i16]>),            // весь сэмпл в RAM (короткие, либо режим Preload)
    Streamed(SampleHead),
}
struct SampleHead {
    head: Arc<[i16]>,                // первые HEAD_FRAMES кадров (interleaved)
    total_frames: u64,
    channels: u8,
    file_id: u32,                    // индекс в таблице открытых файлов loader-потока
}
const HEAD_FRAMES: usize = 65_536;   // 64 Ki кадров; настраивается 32..128 Ki
```

`SamplerEngine.samples: Vec<Arc<[i16]>>` заменяется на `Vec<SampleSource>`; `read_linear_i16`/`read_linear_stereo` читают из головы, а после её конца — из кольца голоса.

### 3.2 Состояние голоса

```rust
struct VoiceStream {
    consumer: rtrb::Consumer<i16>,   // кольцо выделено при старте движка
    generation: u32,                 // отмена устаревших запросов
    next_frame: u64,                 // сколько кадров уже запрошено у диска
    underrun_fade: u16,              // остаток затухания (STEAL_FADE_SAMPLES = 240)
}
const RING_FRAMES: usize = 32_768;   // ~0.68 с @48 кГц на голос
```

Кольца создаются в конструкторе движка для `max_voices` (64–128), не при `note_on`.

### 3.3 Запрос к диску

```rust
#[derive(Clone, Copy)]
struct LoadRequest { voice: u16, generation: u32, sample_index: u32, from_frame: u64, frames: u32 }
```

`Copy`, без указателей и `Drop`. Очередь audio→loader — `rtrb::Producer<LoadRequest>` ёмкостью `2 × max_voices`.

### 3.4 Hot-интерполяция

Голова включает запас `Hermite4` (3 кадра) на стыке голова/кольцо: кольцо начинается с `HEAD_FRAMES - 4`, чтобы интерполяция не видела разрыв.

### 3.5 Почему не mmap в аудиопотоке

`specs/068` запрещает `mmap` (page fault = I/O в аудиопотоке). RFC это подтверждает. Единственный доступ к диску — `pread` в loader-потоке.

## 4. Протокол audio ↔ disk

Аудиопоток:
1. `note_on`: берёт голос, `generation += 1`, читает голову (RAM). Если `total_frames > HEAD_FRAMES`, шлёт `LoadRequest{from_frame: HEAD_FRAMES - 4}` через `try_push`. Переполнение очереди: запрос теряется, `dropped_requests += 1`; голос доиграет голову и уйдёт в underrun-затухание.
2. Каждый блок: если заполнение кольца < 50 % и нет запроса «в полёте», шлёт следующий запрос.
3. `note_off`/кража/конец: `generation += 1` (loader отбросит устаревший блок).

Loader-поток:
- Принимает запросы, сортирует по дедлайну (оставшееся в голове/кольце время), читает блок (16–32 Ki кадров) `pread`-ом в заранее выделенный буфер и пишет в кольцо голоса (`Producer<i16>` у loader-а). Проверяет `generation` перед записью.
- Файлы открыты заранее (таблица `file_id`), лимит дескрипторов: открывать lazily LRU ≤ 256.

Запреты в аудиопотоке: аллокации, `Mutex`, I/O, логирование, `drop` `Arc` (освобождение идёт через retire-кольцо в loader/UI-поток, как в 068).

### 4.1 Underrun

При пустом кольце голос не ждёт: затухание за `STEAL_FADE_SAMPLES` (240 кадров, 5 мс), `underruns: AtomicU32 += 1` (Relaxed), голос освобождается. UI/лог читают счётчик вне аудиопотока.

### 4.2 Быстрые повторные ноты

Голова всегда в RAM, поэтому повторный `note_on` того же сэмпла не ждёт диск. Новый голос получает новое кольцо и свой запрос; старый голос отменяется по `generation`. Loader дедуплицирует первые блоки (кэш последних N блоков «сразу после головы», 4 MiB), чтобы тремоло по одной клавише не читало диск повторно.

### 4.3 Педаль и много голосов

При педали живёт до 64–128 голосов с затуханием release. Нагрузка на диск = голоса × 96 KB/с (stereo 48 кГц i16) ≈ 12 MB/s при 128 голосах — ниже пропускной способности даже HDD, но IOPS важны: блок 32 Ki кадров (128 KiB) даёт ≤ ~100 IOPS. Приоритет запросов — по оставшемуся запасу кольца; при перегрузке голоса с наименьшим запасом получают затухание (стандартная кража `STEAL_FADE_SAMPLES`), счётчики `stolen`, `underruns`, `dropped_requests`.

## 5. PCM-кэш

Расположение: `~/.local/share/sound-pro/banks/<id>/cache/` (Windows: `%LOCALAPPDATA%\sound-pro\banks\<id>\cache\`), через `bank_library::banks_root`.

### 5.1 Заголовок `.pcm` (little-endian, 64 байта)

| Смещение | Поле | Тип |
|---|---|---|
| 0 | magic `SPCM` | [u8;4] |
| 4 | format_version | u16 (=1) |
| 6 | channels | u16 |
| 8 | sample_rate | u32 |
| 12 | reserved | u32 |
| 16 | frames | u64 |
| 24 | src_flac_size | u64 |
| 32 | src_flac_xxh3 | u64 |
| 40 | header_crc | u32 |
| 44 | padding до 64 | |

Далее `frames × channels × 2` байт raw i16 interleaved, начало данных выровнено на 64 байта. Размер файла = `64 + frames × channels × 2` (первая проверка целостности).

### 5.2 Индекс и манифест

`cache/manifest.json` (атомарная запись: `.tmp` + `rename`):

```json
{ "format_version": 1, "bank_id": "osiris", "created": "...", "total_bytes": 2749000000,
  "entries": [ { "sample_id": 17, "src": "Samples/C4_v3.flac", "cache": "000017.pcm",
    "size": 1234567, "xxh3_128": "...", "blake3": "...|null",
    "sample_rate": 48000, "channels": 2, "frames": 308000,
    "src_size": 412345, "src_xxh3": "...", "mtime_ns": 0 } ] }
```

`sample_id → path` — это `entries[].cache` относительно `cache/`. `sample_id` — порядок в `unique` (как в `load_bank_with_hint_impl`); устойчивый ключ — `src`, поэтому при несовпадении индексов перестраиваем по `src`.

### 5.3 Генерация

- В `download_bank_into_inner` после распаковки/проверки SFZ: параллельно (`available_parallelism`, как `decode_all`) `decode_sample` → запись `.pcm.tmp` → fsync → `rename`. Память: один декодированный файл на поток, без накопления банка.
- Прогресс: callback `(done, total, bytes)` в существующий канал прогресса загрузки.
- Перед стартом — проверка свободного места (≥ `Σ frames × ch × 2` + 5 %); иначе понятная ошибка и режим C (FLAC по блокам) / отказ.
- Если кэша нет при загрузке инструмента: фоновое построение с UI-прогрессом, после завершения инструмент грузится из кэша. Следующие запуски быстрые.
- Кэш — производные данные: удаление `cache/` безопасно, FLAC остаются источником правды.

## 6. Integrity

Требование владельца: целостность файлов инструмента проверяется при каждой загрузке.

### 6.1 Уровни проверки

| Уровень | Что проверяет | Стоимость (1242 файла, 2.6 GB) |
|---|---|---|
| L0 (всегда, синхронно) | манифест читается, `format_version`, версия совпала; существование файла; `size == 64 + frames×ch×2`; заголовок (magic, crc, rate/ch/frames == манифест) | 1242 × `stat` + чтение 64 байт ≈ 50–200 мс |
| L1 (всегда, фоном) | mtime vs манифест; выборочный хэш: первые 64 KiB + последние 64 KiB + 1–2 случайных блока по 64 KiB (xxh3) | ≈ 1242 × 256 KiB ≈ 320 MB чтения, ~0.3–1 с (тёплый кэш ОС), 3–5 с на HDD |
| L2 (полный, фоном) | полный xxh3-128 всех файлов | xxh3 ≥ 10 GB/s, лимит — диск: 0.3–1 с (кэш ОС), ~2–5 с на SATA SSD, 20–30 с на HDD |
| L3 (по запросу/после сбоя) | blake3 PCM + xxh3 исходного FLAC против манифеста | 2–5 с CPU на PCM, +460 MiB FLAC |

Политика: L0 + L1 при каждой загрузке инструмента; L2 — при первом запуске после старта приложения (раз за сессию) и всегда после аварийного завершения (маркер `cache/.dirty` создаётся перед записью, удаляется после); L3 — кнопка «Проверить банк» и при подозрении. Так «каждая загрузка» покрыта дешёвой гарантией, а полный хэш не заставляет ждать.

Почему не только размер+mtime: усечение ловится по размеру, но бит-флип/тихая порча диска — нет; выборочный хэш ловит большую часть реальных повреждений (обрыв записи, нулевые хвосты), полный — всё.

### 6.2 Влияние на время загрузки

- L0 блокирует старт на ≤ 0.2 с.
- L1 и L2 идут в фоне параллельно с формированием голов; инструмент доступен для игры после L0 и загрузки голов. Файл, не прошедший проверку, помечается `quarantined`: его регионы не играются (голос не стартует, `dropped_starts`), пока файл не пересобран.
- Загрузка голов: чтение 1242 × 128 KiB ≈ 150 МиБ, ~0.5–2 с (тёплый/холодный SSD).
- Итого холодный запуск Osiris ≈ 2–4 с до игры (против десятков секунд сейчас); пересборка не блокирует.

### 6.3 Автоперестроение

Файл, не прошедший проверку:
1. помечается `quarantined`, логируется (`log_warn!`: банк, файл, причина, ожидаемое/фактическое);
2. фоновый воркер декодирует исходный FLAC (`decode_sample`) → `.tmp` → `rename`, обновляет запись манифеста;
3. если FLAC тоже отсутствует/не совпадает с `src_xxh3` — файл помечается `unrecoverable`, предлагается «Скачать банк заново» (`download_bank`).
Перестроение идёт низким приоритетом (1–2 потока), чтобы не мешать аудио.

### 6.4 UI и лог

- Тост/строка статуса: «Проверка банка… N/M», «Повреждено K файлов — восстанавливаю из FLAC (done/total)», «Банк восстановлен» / «Не удалось восстановить K файлов».
- Итог проверки в лог: `log_info!` время по уровням, число проверенных/повреждённых/восстановленных; ошибки — `log_error!`.
- Отчёт доступен в диалоге банка (список quarantined).

### 6.5 Выбор хэша

xxh3-128 для рутинной проверки (быстрый, не криптографический; цель — обнаружение порчи, не атак); blake3 опционален и считается при построении кэша и L3. Новые зависимости (`xxhash-rust`, `blake3`) — только в `crates/daw-app`, не в `audio-core`.

## 7. Бюджет памяти (Osiris)

| Статья | Расчёт | MiB |
|---|---|---|
| Головы | 1242 × ≤128 KiB (stereo, 64 Ki кадров = 256 KiB!) | ≤ ~160 при HEAD=32 Ki кадров stereo; ≤ 310 при 64 Ki |
| Кольца | 128 голосов × 32 Ki кадров × 2 ch × 2 B | 16 |
| Блок-кэш loader | 4 MiB + буферы | ~8 |
| Манифест/индексы | 1242 записи | < 2 |
| Приложение/GUI/прочее | | ~100–150 |
| Итого | HEAD = 32 Ki кадров | ≈ 290–340 |
| Итого | HEAD = 64 Ki кадров | ≈ 440–490 |

Примечание: «64–128 KiB» считаются по байтам одного канала; для stereo i16 `HEAD_FRAMES = 32_768` ≈ 128 KiB. Рекомендуется `HEAD_FRAMES = 32_768` по умолчанию, адаптивно: бюджет памяти `streaming_budget_mib` (по умолчанию 400) делится между головами; при большой RAM — режим `Resident` для коротких сэмплов. Проверяем в тестах: `Σ head_bytes + voices × RING × ch × 2 ≤ budget` (формула 068).

Время головы: 32 Ki кадров = 0.68 с — достаточно для задержки loader-а при холодном диске; для HDD увеличить `HEAD_FRAMES` до 64 Ki.

## 8. Миграция от `LoadedBank`

1. Шаг 0 (без изменения поведения): ввести `SampleSource` с единственным вариантом `Resident`; `LoadedBank.samples: Vec<Arc<[i16]>>` оборачивается; golden/тесты зелёные без изменений.
2. Добавить кэш-генерацию и `load_bank_from_cache` (чтение `.pcm` в `Resident`, без FLAC). Режим «весь кэш в RAM» остаётся для банков ≤ бюджета (Salamander ~1.1 GiB при бюджете ≥ 1.2 GiB).
3. Режим `Stream` включается автоматически, если `Σ PCM > streaming_threshold` (по умолчанию: доступная RAM / 4 или > бюджета); принудительно — настройкой.
4. `LoadedBank` становится `{ regions, sources: Vec<SampleSource>, warnings, decode_failures, ram_bytes, cache: Option<CacheHandle> }`; `ram_bytes` считает только резидентные данные.
5. Fallback: нет кэша и нет места на диске → вариант C (FLAC по блокам) или отказ с сообщением; `build_instrument` по-прежнему откатывается на встроенное пианино с причиной.
6. Старые пользовательские банки без `cache/` строят кэш при первой загрузке (§5.3). Формат `format_version` проверяется; новая версия → перестроение.

## 9. Golden и офлайн-экспорт

- `crates/audio-core/tests/golden/*.wav` не меняются и не пересоздаются; DSP-путь чтения из `Resident` побитово идентичен текущему.
- `SamplerInstrument::render_notes` (офлайн, экспорт) использует `Resident` либо `SyncStream` (чтение блока синхронно в том же потоке; underrun = 0). Результат бит-в-бит равен `Resident` — тест эквивалентности «Preload vs Stream render» обязателен.
- Экспорт Osiris полной загрузкой требует ~2.6 GiB; допустим `SyncStream` как режим по умолчанию на малой RAM (медленнее, зато в пределах бюджета).
- Тесты — без аудиоустройства (offline-рендерер).

## 11. Риски

| Риск | Митигация |
|---|---|
| Кэш занимает ~2.6 GiB на диске (против 460 MiB FLAC) | проверка свободного места, UI-предупреждение, возможность удалить кэш; режим C как fallback |
| Холодный HDD: латентность > длины головы | `HEAD_FRAMES` до 64 Ki, read-ahead, предзагрузка кольца; underrun-счётчик и затухание вместо блокировки |
| Underrun при 128 голосах + педаль | приоритеты по запасу кольца, кража голосов, лимит голосов в режиме Stream |
| Порча кэша / обрыв записи | атомарный `rename`, `.dirty`-маркер, integrity L0–L3, автоперестроение |
| Фоновая проверка/перестроение мешают аудио | 1–2 потока низкого приоритета, ограничение скорости чтения |
| Конфликт с запретом mmap в 068 | mmap не используется; `pread` только в loader |
| Дескрипторы (1242 файла), особенности Windows | lazy-open LRU ≤ 256, тесты на Windows |
| Разные `sample_rate`/каналы в банке | хранятся в заголовке; ресемплинг в `resolve` как сейчас |
| Рассинхрон `sample_id` при смене SFZ | ключ по `src`, перестроение индекса |
| Тихая порча без обнаружения L1 | полный xxh3 раз за сессию и после сбоя; L3 по запросу |

## 12. Открытые вопросы

1. Дефолт `HEAD_FRAMES` (32 Ki vs 64 Ki) — подобрать замерами на HDD.
2. Хранить blake3 всегда или только по запросу (стоимость при построении ≈ +2–5 с)?
3. Нужен ли режим C (FLAC по блокам) в первой версии или достаточно ошибки «нет места под кэш»?
4. Порог автопереключения Resident/Stream (доля доступной RAM).

## 13. Итог

Выбран гибрид: PCM-кэш, создаваемый при скачивании, + стриминг голов/колец для банков, не помещающихся в бюджет; Resident-режим для малых банков. Osiris ≈ 300–450 MiB RSS, загрузка секунды, аудиопоток без I/O, целостность проверяется при каждой загрузке (L0+L1 всегда, L2 раз за сессию), golden и экспорт не затронуты.

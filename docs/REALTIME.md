# Контракт реального времени

## Почему это главное правило

Аудиоколбэк работает в жёстком дедлайне: на 48 кГц при буфере 256 сэмплов это
5,3 мс. Если колбэк опоздает хоть раз, пользователь услышит щелчок (xrun).
Поэтому в колбэке запрещены аллокации, блокировки и системные вызовы: любая
аллокация может взять мьютекс аллокатора, а любой `/proc`-опрос — диск.

## Граница

```
UI / агент / CLI                     аудиопоток
─────────────────                    ──────────
создаёт узлы       ─ rtrb (setup) ─► Graph (готов)
TransportCommand   ─ rtrb (SPSC)  ─► Transport::apply
RenderStats::frames ◄─ atomics ───── fetch_add
```

- Всё, что создаёт `Vec` или `Box`, происходит в контрольном потоке.
- Ёмкость `rtrb`-очередей и scratch-буферов фиксируется при создании.
- При переполнении очереди команда **отбрасывается** (try-push), а не ждёт.
- Ошибки на горячем пути возвращаются как `Result`, не паника.

## Чек-лист ревью для агента

- [ ] Нет `Vec::new`, `push`, `Box::new`, `format!`, `to_string`, `collect` в
      функциях, вызываемых из `NodeProcessor::process`.
- [ ] Нет `std::fs`, `std::env`, `println!`, `eprintln!`, `dbg!`.
- [ ] Нет `Mutex`, `RwLock`, `std::sync::mpsc`, `.await`.
- [ ] Нет `unwrap`/`expect` на данных, зависящих от входа.
- [ ] Scratch-буферы создаются в конструкторе, а не при первом вызове.

## Проверка

`cargo test` покрывает движок через offline-путь. Для дополнительной проверки
аудиопотока в будущем: `loom` для SPSC-протокола, `heaptrack`/`valgrind
--tool=massif` на релизной сборке с реальным бэкендом.

## Запись на диск

`audio_core::wav::Recorder` делает файловый ввод-вывод на каждый `write`,
поэтому **не вызывается** из `Graph::process`/`Renderer::render`. В
offline-рендере он работает в том же потоке, что и рендер (горячего пути нет);
в реальном времени сэмплы передаются в fallback-поток через SPSC-очередь
(SPEC-003), и только там попадают в `Recorder`.

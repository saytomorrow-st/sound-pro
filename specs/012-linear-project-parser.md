# SPEC-012: линейный разбор проекта

Статус: implemented
Владелец: saytomorrow
Для агента: разрешено реализовывать

## Проблема

`Project::from_json` разбирает длинную строку за квадратичное время. Замер
(release): строка из 50 000 символов разбирается за 0,06 с, из 400 000 — за 6,5 с.
Файл проекта в 1 МБ с одной длинной строкой (например, вставленное в `name`
описание) нарушает требование SPEC-008 «< 1 с, без паники». Массивы и
пробелы растут линейно.

## Поведение

- Время `from_json` растёт линейно от размера текста при любом его
  содержимом: длинные строки, длинные массивы, длинные пробельные хвосты.
- Результаты разбора и ошибки (`Malformed { at }`, `Unsupported { at }`,
  `NameTooLong` и т. д.) не меняются: те же входы дают те же ответы.
- Многобайтовый UTF-8 внутри строк по-прежнему проходит как есть.

## Граничные случаи

| Случай | Ожидаемое поведение |
|---|---|
| `name` из 1 МБ ASCII | `Err(NameTooLong)`, < 1 с |
| `name` из ~1 МБ кириллицы | `Err(NameTooLong)`, < 1 с |
| незакрытая строка длиной 1 МБ | `Err(Malformed { at })`, < 1 с |
| массив из ~1 МБ чисел в `params` | `Err`, < 1 с |
| многобайтовый символ в имени | round-trip без изменений |
| обрезанный UTF-8 внутри строки (невалидный текст на входе невозможен, `&str`) | не применимо |

## Критерии приёмки

- [x] Интеграционные тесты на каждую строку таблицы с порогом < 1 с
      (в debug-сборке, как остальные тесты скорости SPEC-008).
- [x] Тест на длинную строку падает на старой реализации (проверено мутацией).
- [x] Все существующие тесты `project` зелёные без изменений.
- [x] `cargo clippy -- -D warnings` и `cargo test` зелёные.

## Вне области

- Потоковый разбор и чтение файла по частям.
- Поднятие лимитов `MAX_TRACKS`, `MAX_CLIPS_PER_TRACK`, `MAX_NAME_BYTES`.
- Ускорение константы (SIMD, `memchr`): нужна только линейность.

# SPEC-005: Realtime-бэкенд CPAL (Linux ALSA / Windows WASAPI)

Статус: implemented
Владелец: команда платформы
Для агента: разрешено реализовывать

Файлы: `crates/daw-app/src/realtime.rs` (новый модуль), `crates/daw-app/src/lib.rs`,
`crates/daw-app/src/main.rs`, `crates/daw-app/Cargo.toml`, `.github/workflows/ci.yml`,
`docs/`, `crates/daw-app/tests/`

Разрешённый рефакторинг: перенести inline-модуль `pub mod realtime` из `lib.rs`
в отдельный файл `src/realtime.rs` и переименовать `BackendError` →
`RealtimeError`. Публичный путь `daw_app::realtime::*` сохраняется.

## Проблема

`play_default` в `crates/daw-app/src/realtime.rs` — минимальный прототип: он не
учитывает фактический размер колбэка устройства, не сообщает dropped callbacks и
не умеет остановиться.

## Поведение

1. При старте выбирается конфигурация устройства с sample rate из
   `DEFAULT_SAMPLE_RATE` (48 кГц), иначе ближайшая поддерживаемая; выбор
   логируется в stderr (это fallback-поток, не аудио).
2. Колбэк: если `frames > max_quantum`, квант рендерится по частям без аллокации;
   недостающие каналы заполняются тишиной; выход дублируется из моно.
3. Счётчики `dropped_callbacks` и `rendered_frames` ведутся атомиками и
   доступны через `RealtimeHandle::stats()`.
4. `RealtimeHandle::stop()` останавливает поток без паники и join-ится < 100 мс.
5. Ошибки устройства — `Result<_, RealtimeError>`, не `panic!`/`unwrap`.
6. CI-джоба `realtime-build` собирает фичу на Linux и Windows (уже есть).

## Граничные случаи

| Случай | Ожидаемое поведение |
|---|---|
| нет аудиоустройства | `RealtimeError::NoDevice`, код выхода 2 у CLI |
| устройство только стерео | моно дублируется в оба канала |
| частота 44.1 кГц | используется она, транспорт идёт на её частоте |
| рендер вернул ошибку | тишина в колбэке, счётчик ошибок +1 |
| ошибка устройства | колбэк ошибки только инкрементит `stream_errors`; отчёт — в `stop()` |
| два вызова `stop()` | второй — no-op |

## Ручная проверка: `daw bounce` и `daw play` дают одинаковый звук

`daw bounce` и `daw play` собирают один и тот же демо-граф
(`daw_app::build_demo_graph`: синус 440 Гц, амплитуда 0.5, моно) и прогоняют его
через один и тот же `audio_core::Renderer`. Offline-путь пишет WAV, realtime-путь
отдаёт те же сэмплы в устройство. Полное совпадение с точностью до
разрядности/частоты устройства подтверждается так (на машине с ALSA, фича
`realtime`):

1. Собрать с фичей:
   ```bash
   cargo build -p daw-app --features realtime
   ```
2. Отрендерить эталон и записать реальный выход:
   ```bash
   # эталон: 3 секунды в WAV (48 кГц, моно)
   cargo run -q --bin daw -- bounce /tmp/ref.wav 3.0
   # реальный выход устройства -> тот же сигнал; слушаем 3 секунды
   cargo run -q --bin daw -- play 3.0
   ```
3. Сравнить визуально/на слух: тон 440 Гц одинаков, огибающая та же; либо
   захватить выход через loopback-устройство в WAV и сравнить формы сигнала
   (допуск по амплитуде `1e-3`, по частоте — совпадение 440 Гц). При устройстве
   «только 44.1 кГц» `daw play` печатает выбранную частоту в stderr; транспорт
   идёт на 44.1 кГц, тон остаётся 440 Гц.

Ожидаемое: одинаковый тембр и высота; счётчики `daw play` в конце —
`rendered_frames > 0`, `render_errors == 0`, `dropped_callbacks == 0` на
исправном устройстве.
